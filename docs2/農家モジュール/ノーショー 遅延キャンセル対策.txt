ノーショー・遅延キャンセル 完全仕様書

基本設計思想
ノーショー（農家報告）と遅延キャンセル（ユーザー自身による3時間以内キャンセル）を同一のペナルティカウンターで管理する。過去1年間のローリングウィンドウで集計し、合計3回でアカウントを永久BAN。自己解除（pardon）制度はない。

ノーショー（農家からの報告）
誰がトリガーするか
農家が FarmerReservationTable 画面の詳細モーダルから「無断キャンセル報告」ボタンを押す。
タイムロック（報告できる時間帯）

受け渡し終了時刻になるまでボタン自体が画面に存在しない
終了時刻ジャストでボタンが出現する
終了時刻から12時間後に全ボタンが消滅し、以降は閲覧専用になる
この設計により「まだ時間内なのに間違えてノーショーを押す」事故と「翌朝に記憶が曖昧な状態で当てずっぽうに報告する」事故を両方防いでいる

農家側のリミッター（冤罪防止）
農家1アカウントにつき過去30日間で最大2回までしか報告できない。3回目以降はバックエンドが400エラーを返して弾く。これにより悪意のある農家が特定ユーザーを不当にBANさせることを物理的に防いでいる。
DBへの記録
reservations.status が 'confirmed' → 'no_show' に更新される。
ペナルティカウントへの算入
state_repo.py の集計クエリ：
sqlSELECT COUNT(*) FROM reservations
WHERE consumer_id = ?
  AND status = 'no_show'
  AND created_at >= datetime('now', '-1 year')
```
`created_at`（予約作成日）が1年以上前になった時点で自動的に集計から外れる。

### 取り消し（農家による救済）
農家は「報告を取り消す（confirmedに戻す）」ことができる。遅刻して現れたユーザーを救済するための機能。取り消すと `status` が `'confirmed'` に戻り、ペナルティカウントも下がる。

## 遅延キャンセル（ユーザー自身による3時間以内のキャンセル）

### 何が「遅延キャンセル」か
ユーザーがキャンセルを実行した時点で `now >= event_start_at - 3時間` であれば遅延キャンセルと判定される。受け渡し開始の3時間より前にキャンセルした場合は通常キャンセルとなりペナルティカウントに算入されない。

### キャンセルができる時間帯
`cancel_service.py` の判定：`now < event_start_at` である限りキャンセル可能。受け渡し開始時刻を過ぎると物理的にキャンセル不可になる（APIが `NotCancellableError` を返す）。

つまりペナルティが発生しうる時間帯は「`event_start_at - 3時間` から `event_start_at` まで」の3時間の窓だけである。

### ユーザーへの警告表示（CancelConfirmPage）

**通常キャンセル（3時間より前）の場合：**
```
キャンセルを実行すると、この予約は取り消されます。
お米代のお支払いは発生しません。
```
ボタンは「キャンセルを確定する」（黒）

**遅延キャンセル（3時間以内）の場合：**
```
受け渡し時刻まで3時間を切っています。

【農家さんへのご配慮をお願いします】
農家さんはご予約日に合わせて精米を行っています。精米されたお米は
他への販売が難しく、キャンセルされると農家さんが処理に困ってしまいます。
やむを得ないご事情を除き、できるだけキャンセルはお控えください。
※受け渡し直前のキャンセルが重なった場合は、次回以降のご購入を
  制限させていただく場合があります。
ボタンは「やむを得ない事情のためキャンセルする」（赤）
この警告は毎回・即座に・ページ表示と同時に表示される。ボタンを押して初めて出るのではなく、ページを開いた瞬間に既に見える状態になっている。警告を見た上でボタンを押すことが暗黙の同意とみなす設計。
DBへの記録（2段階）
① status の更新
reservations.status が 'confirmed' → 'cancelled' に更新される。通常キャンセルと同じ値なので status だけでは区別できない。
② is_late_cancel フラグの書き込み
cancel_service.py が遅延キャンセルと判定した場合、state_repo.mark_late_cancel() を呼び reservations.is_late_cancel = 1 を書き込む。このフラグによって「3時間以内のキャンセルだけ」を後から集計できる。
フラグの書き込みは Best Effort 設計になっており、書き込みに失敗してもキャンセル自体は完了する。エラーはログに記録されるだけ。
ペナルティカウントへの算入
sqlSELECT COUNT(*) FROM reservations
WHERE consumer_id = ?
  AND is_late_cancel = 1
  AND created_at >= datetime('now', '-1 year')
created_at（予約作成日）が1年以上前になった時点で自動的に集計から外れる。

ペナルティの合算と状態遷移
合算の仕組み（state_service.py）
pythonpenalty_count = ns_count + lc_count  # no_show件数 + 遅延キャンセル件数
penalty_status = "banned" if penalty_count >= 3 else "none"
```

no_showと遅延キャンセルを区別せず単純に足す。例えば「no_show 1回 + 遅延キャンセル 2回」でもBANになる。

### 状態は2つのみ

**none（正常）**
`penalty_count` が 0、1、2 のいずれか。予約・購入のすべての機能が通常通り使える。

**banned（永久BAN）**
`penalty_count` が 3以上。以下の2箇所で物理的にブロックされる。

## BANのブロック（2重の関所）

### 関所① UI層（ConfirmPage.tsx）
ページ読み込み時に `fetchConsumerState()` を呼び、`penalty.status === "banned"` であれば予約フォームを一切表示せず以下のみを表示する：
```
現在、このアカウントからはご予約手続きを行うことができません。
グレー背景、理由なし、問い合わせ先なし。悪質なユーザーに「なぜBANされたか」を伝えず、クレームや粘着を防ぐ設計。
関所② API層（stripe_checkout_api.py）
仮にUI層を不正にすり抜けて /stripe/checkout/from-confirm を直接叩いたとしても、バックエンドで再度 StateService.get_state() を実行し、banned であれば 403 Forbidden を返してブロックする。

1年ローリングの具体的な動き
created_at >= datetime('now', '-1 year') はSQLite側で動的に計算される。例えば2025年4月1日にno_showが記録された場合、2026年4月1日の日付が変わった瞬間からそのレコードが集計対象外になり、penalty_count が自動的に1減る。
DBのレコード自体は削除されない。あくまで集計から外れるだけ。したがってペナルティカウントが3未満に戻った時点でBANが自動解除され、次回の get_state() 呼び出しから penalty_status = "none" として返される。

現在「ない」仕様

pardon（自己解除）制度：廃止。BANは1年間自然消滅を待つしかない
locked状態：廃止。none と banned の2状態のみ
no_showとlate_cancelの個別閾値：廃止。合算して3回
BANの通知メール：実装なし。ユーザーは予約しようとしたときに初めて気づく
管理者による手動BAN解除：admin APIには現在この機能はない

📘 Komet 予約・決済アーキテクチャ設計書 (JIT PENDING 構成)最終更新: 2026-02-03対象バージョン: V2 (JIT Implementation)1. 設計思想と概要本システムは、「Just-In-Time (JIT) PENDING 生成モデル」を採用している。
これは、「ユーザーが『支払う』ボタンを押すその瞬間まで、予約テーブル（reservations）を汚さない」 という原則に基づく設計である。従来の課題 (Before)画面遷移（Bridge）のたびに PENDING レコードを作成していた。「買うか迷っているだけ」のユーザーのゴミデータが大量発生していた。Draft（Session）と PENDING（DB）の二重管理が発生し、整合性が脆かった。現在の構造 (After)UIの真実: confirm_sessions (JSON Draft) が唯一の正解。業務の真実: reservations テーブル。接続点: Stripe決済を開始する API (/stripe/checkout/from-confirm) の中でのみ、Draft から PENDING へ変換される。2. データフロー（The Happy Path）ユーザーが予約を完了するまでのデータの流れは以下の通り。Phase 1: ドラフト作成 (UI Layer)FarmDetail: ユーザーが「予約へ進む」を押す。API: POST /api/confirm/sessionsconfirm_sessions テーブルに draft_json を保存。まだ reservations テーブルには何もしない。Confirm Page:GET /api/confirm/sessions/{cs}/context を叩く。Draft JSON を元に、最新価格で再計算して画面描画。重要: ここでは reservations テーブルを一切参照しない。Phase 2: JIT 確定 (Transaction Boundary)User Action: 「予約確定（Stripeへ）」ボタンを押す。API: POST /stripe/checkout/from-confirm (ここが核心)① confirm_session_id (cs) の冪等性をチェック（既にPENDINGがあれば再利用）。② なければ、Draft JSON を読み込み、この瞬間に INSERT INTO reservations (PENDING) を実行。③ 作成された reservation_id を持って Stripe Checkout Session を発行。Phase 3: 決済完了 (Finalization)Stripe Webhook: checkout.session.completedMetadata に含まれる confirm_session_id をキーにして PENDING を検索。Status を CONFIRMED に更新。confirm_sessions のステータスを consumed に更新。3. 自動クリーニング (Garbage Collection)JIT構成によりゴミは激減したが、「決済画面まで行って離脱したユーザー」の PENDING は残る。これを放置しないための仕組みを導入済み。実行タイミング: アプリケーション起動時 (main.py の lifespan)ロジック: app_v2/maintenance/cleanup.pyルール:Status = 'PENDING'Created_at < 現在から 7日前上記に該当するレコードを 物理削除 (DELETE) する。これにより、DB容量の圧迫を防ぎつつ、直近1週間のトラブルシューティング用ログ（離脱痕跡）は保持される。4. 開発・保守マニュアル🚫 禁止事項 (Don'ts)Confirmページで reservations を読みに行かないことConfirm時点では予約レコードは存在しない保証がある。必ず confirm_sessions (Draft) を読むこと。旧API reservations_pending_api.py は削除済み。復活させてはならない。Webhook で INSERT しないこと在庫ロック（Over-selling防止）のため、Stripeへ行く「前」にレコードを作る（JIT PENDING）運用を厳守する。「Webhookで初めてレコードを作る」設計に変えると、在庫管理事故のリスクが高まる。✅ 変更時のチェックリスト (Do's)スキーマ変更やロジック変更時は、以下を確認する。[ ] Confirmの価格計算: confirm_session_api.py (Draft読み出し) と stripe_checkout_from_confirm_api.py (JIT生成) の両方で、価格計算ロジックが一致しているか？[ ] GCの安全性: cleanup.py の期間設定（デフォルト7日）が、現在の運用フェーズに対して適切か？[ ] 冪等性: from-confirm API は、連打されても reservation_id が1つしか発行されないようになっているか？（現状は confirm_session_id による重複チェックあり）5. 主要ファイル構成このアーキテクチャを支える主要なファイル群。ファイルパス役割重要度app_v2/customer_booking/api/confirm_session_api.pyDraft管理 & UI表示用データ提供。ConfirmPageはここを見る。⭐⭐⭐app_v2/integrations/payments/stripe/stripe_checkout_from_confirm_api.pyJIT PENDING生成の心臓部。ここで初めて予約レコードが生まれる。⭐⭐⭐app_v2/maintenance/cleanup.py掃除屋。起動時に古いPENDINGを消す。⭐⭐app_v2/integrations/payments/stripe/stripe_webhook_service.py決済完了処理。PENDINGをCONFIRMEDにする。⭐⭐frontend/src/pages/public/Confirm/ConfirmPage.tsxUI。Draftデータを表示し、決済トリガーを引く。⭐⭐6. 将来の拡張性（FAQ）Q: 在庫管理を厳密にしたくなったら？A: 現在の「JIT PENDING」は在庫ロックと相性が良いです。stripe_checkout_from_confirm_api.py の INSERT 直前で在庫数チェック（SELECT count... FOR UPDATE 等）を入れるだけで対応可能です。Q: PENDINGのゴミをもっと早く消したい/残したいA: app_v2/main.py の lifespan 内にある run_pending_gc(retention_days=7) の数値を変更するだけで調整可能です。Q: 分析のために離脱データが必要になったら？A: 現在のGCは物理削除です。もし分析が必要なら、GCロジックを DELETE ではなく UPDATE status='archived' に変更するか、別途ログテーブルに退避させる改造を行ってください。
